คุณสมบัติเหล่านี้ต้องใช้คอนโทรลเลอร์และ CLI จากรีวิชันที่มีคู่มือนี้ การเปรียบเทียบการตั้งค่าอย่างตรงกันและการส่งต่อยังต้องใช้ตัวเล่นที่อัปเดตแล้วด้วย ไฟล์เก็บรุ่นเก่าและรีวิชัน CLI ในอดีตจากคู่มือติดตั้งไม่ได้รับคุณสมบัติเหล่านี้โดยอัตโนมัติ ให้ติดตั้ง**ไฟล์ `cli/*.py` ทั้งหมดพร้อมกัน** รวมถึง `preset_session.py` และรักษาการตั้งค่าส่วนตัวไว้

## เปิดใช้ผลลัพธ์ที่เก็บถาวรภายในขอบเขต

เพิ่มบล็อกทางเลือกนี้ในการตั้งค่าเซิร์ฟเวอร์ส่วนตัว จากนั้นตรวจสอบและเริ่มเซิร์ฟเวอร์ใหม่ เลือกพาธสัมบูรณ์บนระบบไฟล์ถาวรภายในเครื่องที่บัญชีบริการเขียนได้ บน Unix ไดเรกทอรีต้องเป็นส่วนตัว (0700) และไฟล์บันทึกกับไฟล์ล็อกที่มีอยู่ต้องเป็นไฟล์ปกติส่วนตัว (0600) บน Windows จำกัด ACL ของไดเรกทอรีให้เฉพาะบัญชีบริการ กระบวนการเดียวเป็นเจ้าของบันทึกหนึ่งชุด

```json
"journal": {
  "path": "/var/lib/ottplay-control/private/operations.json",
  "max_records": 1024,
  "retention_seconds": 86400
}
```

เซิร์ฟเวอร์สร้างไดเรกทอรีที่ขาดด้วยโหมด 0700 ขอบเขตคือ 1–4096 รายการ, 60–86400 วินาที และ 4 MiB บนดิสก์ ระยะเก็บต้องครอบคลุม `command_ttl_seconds` เมื่อบันทึกเต็มจะปฏิเสธการทำงานใหม่ที่มีคีย์ แทนการขับรายการที่ยังใช้ได้ออก ไฟล์เสีย ไดเรกทอรี Unix ที่ไม่ปลอดภัย ผู้เขียนรายอื่น หรือการเขียนถาวรล้มเหลว ทำให้ระบบปฏิเสธอย่างปลอดภัย ค่าเริ่มต้นยังเป็นเส้นทางคำสั่งเดิมในหน่วยความจำ

ยูนิต systemd ที่ให้มาสร้าง `/var/lib/ottplay-control` ด้วยโหมด 0700 สำหรับ Compose ให้เตรียมไดเรกทอรีโฮสต์ที่ UID 65532 เป็นเจ้าของ ตั้ง `CONTROL_SERVER_STATE` เป็นพาธสัมบูรณ์ และใช้ `deploy/compose.yml` ร่วมกับ `deploy/compose.journal.yml` ไฟล์หลังเพิ่มเฉพาะเมานต์สถานะที่เขียนได้ ระบบไฟล์รากยังอ่านอย่างเดียว สำหรับ Helm ให้เตรียม persistent claim แยกต่างหากและตั้ง `journalExistingClaim=CLAIM_NAME` claim เมานต์ที่ `/var/lib/ottplay-control` ให้ใช้ไดเรกทอรีย่อยส่วนตัวตามตัวอย่างข้างต้น chart คงหนึ่ง replica, `Recreate` และ `fsGroupChangePolicy: OnRootMismatch` เพื่อไม่ให้การเมานต์ใหม่ขยายสิทธิ์ไดเรกทอรีส่วนตัวที่สร้างไว้แบบเรียกซ้ำ ตรวจว่าไดรเวอร์จัดเก็บที่เลือกสนับสนุนความหมายของความเป็นเจ้าของนี้ chart ไม่สร้างหรือลบ claim และการเปิดเมานต์ไม่ได้เปิดบันทึก การตั้งค่าเซิร์ฟเวอร์ส่วนตัวยังคงเป็นผู้ควบคุม

สำหรับ `POST /api/requests` ให้เพิ่ม `idempotency_key` ข้าง `action` และ `params` ส่วน POST คำสั่งแบบเก่ายอมรับ `Idempotency-Key` แทน คีย์ประกอบด้วยตัวอักษร ASCII ตัวเลข ขีดล่าง หรือขีดกลาง 16–80 ตัว ให้สร้างคีย์สุ่มใหม่สำหรับแต่ละเจตนา เจ้าของ/คีย์เดียวกันพร้อมอุปกรณ์ การกระทำ และเนื้อหา JSON ที่ปรับรูปแบบแล้วเหมือนกัน จะคืน ID เดิมโดยไม่เข้าคิวซ้ำ เปลี่ยนเนื้อหาจะได้ 409 ขอบเขตคีย์อิง ID ผู้ดำเนินการหรือผู้ดูแล ไม่ใช่อุปกรณ์ เมื่อหมดระยะเก็บ คีย์อาจถูกยอมรับเป็นเจตนาใหม่ ดังนั้นไคลเอนต์ต้องไม่ลองเจตนาเดิมซ้ำนอกช่วงนั้น

`GET /api/operations?device_id=DEVICE` รายงานว่าเปิดบันทึกหรือไม่ ขอบเขต และ TTL คำสั่ง เพิ่ม `&key=KEY` เพื่ออ่านการทำงาน:

- `pending`: ยอมรับแล้ว แต่ยังไม่มีคำตอบที่เก็บไว้
- `responded`: ได้รับคำตอบจากตัวเล่นที่ผ่านการตรวจสอบแล้ว `result_status` เป็น `ok`, `rejected` หรือ `unsupported` เนื้อหาผลลัพธ์เดิมยังหมดอายุตามปกติ
- `acknowledged`: ผู้รับแบบเก่ายืนยันคำสั่งแล้ว ไม่ได้พิสูจน์ว่ามีภาพการเล่นหรือบันทึกการเปลี่ยนการตั้งค่าแล้ว
- `unknown`: พ้นกำหนดหรือเซิร์ฟเวอร์เริ่มใหม่ก่อนเก็บคำตอบ เซิร์ฟเวอร์**ไม่เรียกคำสั่งนี้ซ้ำเด็ดขาด**หลังเริ่มใหม่

POST ซ้ำที่มีคีย์จะคืน `status: retained`, ID เดิม และสถานะ ส่วน POST ใหม่ทั่วไปยังใช้ `status: queued` รายการบันทึกมีเพียงเจ้าของ อุปกรณ์ การกระทำ ID สุ่ม ค่าแฮชเนื้อหา สถานะ และกำหนดเวลา ไม่มีเนื้อหาคำสั่ง URL ผู้ให้บริการ โทเค็น ภาพหน้าจอ หรือเนื้อหาคำตอบ คำสั่งที่รออยู่ไม่ถูกเก็บถาวร นี่คือการตัดรายการซ้ำและติดตามผลลัพธ์แบบมีขอบเขต ไม่ใช่การทำงานครั้งเดียวอย่างแน่นอน คิวงานถาวร หรือความพร้อมใช้งานสูงหลายเซิร์ฟเวอร์

## วางแผน ใช้ ต่อ และตรวจสอบ Local/Home

พฤติกรรมเดิมของ `ott PLAYER load PRESET` ยังเหมือนเดิม สำหรับขั้นตอนใหม่:

```sh
ott tv load Local plan
ott tv load Local apply
ott tv load Local resume
ott tv load Local verify
```

`plan` ทำงานออฟไลน์ ตรวจพรีเซ็ตภายในเครื่องและแสดงช่องการตั้งค่ากับโปรไฟล์ที่ต้องการให้ใช้งานโดยไม่พิมพ์เนื้อหา ไม่ตรวจตัวเล่น ส่วน `verify` เปรียบเทียบอย่างตรงกันแบบอ่านอย่างเดียวและตรวจโปรไฟล์ M3U ที่เลือก คืนรหัสที่ไม่ใช่ศูนย์หากมีความต่างหรือไม่รองรับการเปรียบเทียบ

`apply` ต้องใช้บันทึกเซิร์ฟเวอร์ โดยสร้างจุดตรวจสอบส่วนตัวและเปรียบเทียบผู้ให้บริการทุกรายที่ตั้งค่าไว้ก่อนแก้ไขครั้งแรก ทุกการบันทึกเปรียบเทียบไบต์ที่เก็บกับค่าที่คาดผ่าน `settings_compare` หากตรงกันจะข้ามการเขียน การตรวจสอบสุดท้ายครอบคลุม Plex ทุกช่อง M3U ช่อง Stalker ทางเลือก และโปรไฟล์ M3U ที่เลือก การเปรียบเทียบคืนค่าบูลีน ไม่คืนความลับที่เก็บไว้

จุดตรวจสอบเริ่มต้นอยู่ใต้ `~/.config/ottplay-control/checkpoints/` ใช้ `--checkpoint /absolute/private/path/session.json` หลังโหมดเพื่อเลือกไฟล์อื่น จุดตรวจสอบมีอุปกรณ์ ชื่อพรีเซ็ต แฮชรีวิชันเซิร์ฟเวอร์/พรีเซ็ต ชื่อขั้นตอนที่เสร็จ และคีย์สุ่มการทำงานที่รออยู่หนึ่งรายการพร้อมกำหนดเวลา ไม่มีค่าการตั้งค่า ไฟล์ถูกแทนที่แบบอะตอมหลัง fsync และล็อกกัน CLI เขียนพร้อมกัน เก็บพรีเซ็ตภายในเครื่องที่ตรงกันให้พร้อมใช้ บน Unix ไดเรกทอรีต้องเป็นส่วนตัว (0700) และไฟล์ปกติใช้ 0600 บน Windows จำกัด ACL ที่สืบทอดของไดเรกทอรีให้ผู้ใช้ที่รัน CLI บิตโหมด Unix ไม่บังคับสิทธิ์การเข้าถึงของ Windows

`resume` ตรวจเซิร์ฟเวอร์ อุปกรณ์ และรีวิชันพรีเซ็ตเดิม แล้วอ่านผลลัพธ์ที่รอ คำตอบที่เก็บไว้ทำให้ตรวจใหม่ได้ทันที ผลลัพธ์ไม่แน่นอนจะหยุดส่งการเปลี่ยนแปลงจนพ้นกำหนดคำสั่งก่อนหน้า เวลารอคำขอ และระยะเผื่อเล็กน้อย จากนั้นรัน `resume` อีกครั้ง มันตรวจการตั้งค่าที่เก็บใหม่แม้ขั้นตอนจะเสร็จแล้ว เพื่อไม่ให้เข้าใจว่าการแก้ของผู้ใช้คือการเขียนสำเร็จครั้งก่อน ไม่เล่นคำสั่งสัมพัทธ์ซ้ำโดยไม่ตรวจสอบ การเลือกผู้ให้บริการ/โปรไฟล์แบบสัมบูรณ์อาจทำซ้ำได้หลังระยะป้องกัน

`apply` ใหม่ไม่เขียนทับจุดตรวจสอบที่มีอยู่ ใช้ซ้ำด้วย `resume` หรือเลือกไฟล์ใหม่เมื่อพรีเซ็ตเปลี่ยน อุปกรณ์ต่างกันมีจุดตรวจสอบแยกกัน ไม่มีธุรกรรมหรือการย้อนกลับที่ครอบคลุมตัวเล่นทั้งหมด การเขียนก่อนหน้าที่สำเร็จยังอยู่เมื่อขั้นตอนหลังล้มเหลว `verified` ยืนยันค่าที่ตัวเล่นเก็บ ณ เวลาเปรียบเทียบ ไม่ใช่การโหลดเครือข่ายสำเร็จหรือภาพ/เสียงจริง

## ให้อินทิเกรชันมีอำนาจเฉพาะที่จำเป็น

ใช้[ผู้ดำเนินการคำสั่งทั่วไป](security-design.md#scoped-command-operators) สำหรับ HA, บริดจ์ RF หรือเอเจนต์ แทนการแจก `admin_token` อนุญาต ID อุปกรณ์ที่ตรงเจาะจงและการทำงานเช่น `input.channel_up` กับ `input.channel_down` ขั้นตอนพรีเซ็ตนี้ต้องให้สิทธิ์ `settings_compare`, `provider`, `profiles`, `status`, `profile`, `profile_settings` และ `provider_settings` อย่างชัดเจนสำหรับการตั้งค่า การส่งต่อต้องมี `playback_handoff_export` ที่ต้นทางและ `playback_handoff_import` ที่ปลายทาง รายการผู้ดำเนินการจับคู่อุปกรณ์กับการกระทำที่ระบุ ใช้ตัวตนแยกกันหากการกระทำเดียวกันไม่ควรใช้กับทุกอุปกรณ์ในรายการ โทเค็นและความยินยอมการวินิจฉัยยังเป็นอำนาจแยกกัน

ผู้ดำเนินการไม่สามารถสำรวจคิวตัวเล่น ส่งคำตอบตัวเล่น แสดงทุกอุปกรณ์ อ่านผลดีบักผู้ดูแล หรืออ่านผลของผู้ดำเนินการอื่น การจำกัดขอบเขตการกระทำยังป้องกันการอ่านการทำงานที่เก็บไว้ของมัน การลบผู้ดำเนินการและเริ่มใหม่จะเพิกถอนข้อมูลรับรอง อย่าใช้ ID ผู้ดำเนินการซ้ำกับอีกตัวตนขณะที่รายการบันทึกเดิมยังอยู่

## เล่นต่อบนตัวเล่นอื่น

```sh
ott handoff living-room bedroom
```

ต้นทางส่งออกการอ้างอิงสด/ย้อนหลังเวอร์ชัน 1 ได้แก่ ผู้ให้บริการ ตัวตนต้นทางแบบทึบแสง ลายนิ้วมือรายการแบบทึบแสง `channel-v1:<8 hex>.<8 hex>` และเวลารายการปัจจุบันสำหรับย้อนหลัง ID ผู้ให้บริการดิบและ URL สตรีมยังอยู่ภายในเครื่อง ปลายทางต้องมี**ต้นทาง/บัญชีที่ตั้งค่าไว้เหมือนกัน** ค้นหารายการที่ตรงอย่างมีเอกลักษณ์ในแค็ตตาล็อกของตน และรับ URL ใหม่ด้วยข้อมูลรับรองภายในเครื่องของตน คอนโทรลเลอร์ไม่คัดลอก URL ที่เล่นได้หรือเปลี่ยนข้อมูลรับรองปลายทาง ต้นทางยังเล่นต่อ ผล CLI สำเร็จหมายถึงปลายทางส่งคำขอแล้ว ไม่ใช่การตรวจจอหรือลำโพงจริง

เวอร์ชัน 1 รองรับแค็ตตาล็อกสด/ย้อนหลังของ `m3u`, `xtream` และ `stalker` เมื่อตัวเล่นให้ตัวตนที่จำเป็นได้ รายการไม่รู้จักหรือกำกวม ต้นทางไม่ตรง และการปฏิเสธนโยบายภายในจะล้มเหลวโดยไม่ใช้ชื่อเป็นทางเลือก VOD/ซีรีส์ การจับคู่ต่างบัญชี การหยุดต้นทางชั่วคราว และการซิงก์ประวัติ/รายการโปรดต่อเนื่องไม่อยู่ในข้อตกลงรุ่นแรกนี้

## แบบฝึกการตรวจสอบและกู้คืน

รัน `go test -race ./...`, `go vet ./...` และ `python3 -m unittest discover -s tests` การทดสอบครอบคลุมคำตอบสูญหายหลังเขียนสำเร็จ การเปรียบเทียบตรงกันก่อนทำต่อ การตั้งค่าคลาดเคลื่อน กำหนดเวลาของการทำงานไม่ทราบผล ผู้เขียนสองราย บันทึกเสีย การอ่านข้ามผู้ดำเนินการ และเนื้อหาส่งต่อผิดรูปแบบ บนตัวเล่นทดสอบ ให้หยุด CLI หลังบันทึกการตั้งค่า เริ่มคอนโทรลเลอร์ใหม่ ทำต่อและตรวจสอบ รวมถึงทดสอบส่งต่อระหว่างต้นทางที่ตรงและไม่ตรงกัน ยืนยันภาพ/เสียงแยกต่างหาก

สำหรับการตรวจสอบภายในเครื่องข้ามรีโพซิทอรี เมื่อมีสำเนา FOSS ปัจจุบันและติดตั้ง dependency สำหรับพัฒนาแล้ว ให้รัน:

```sh
node scripts/smoke_foss_roadmap.cjs /path/to/ottplay-foss
```

การทดสอบ smoke สร้างเซิร์ฟเวอร์ Go นี้ คอมไพล์โครงการ FOSS TypeScript ทั้งหมด และรันระบบขนส่งจริง ตัวจัดการคำสั่ง ตัวตนต้นทาง และโค้เดกเพลย์ลิสต์ที่แจกพร้อมระบบกับ Python CLI มันตรวจค่าการตั้งค่าที่ตรงกันของผู้ให้บริการทั้งสามที่รองรับ ความไม่ตรงกัน การส่งต่อสดที่มี ID แถวภายในเครื่องต่างกัน ออฟเซตค้นหาย้อนหลัง การแก้ URL ล้มเหลว และการตรวจรูปแบบส่งข้อมูลอย่างเข้มงวด มีเพียงที่เก็บข้อมูล นโยบายผู้ให้บริการ และอินเทอร์เฟซโฮสต์เล่นสื่อที่เป็นตัวแทนทดสอบ ไม่ตรวจเบราว์เซอร์ เอาต์พุตสื่อจริง หรือการเข้าถึงบัญชีจริง มันผูกกับ loopback ใช้ไฟล์ชั่วคราวส่วนตัว ไม่ติดต่อ URL สตรีม และลบไฟล์/เซิร์ฟเวอร์ของตนเมื่อจบ
