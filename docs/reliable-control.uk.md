Ці функції потребують контролера та CLI з ревізії, що містить цей посібник. Точне порівняння налаштувань і передавання також потребують оновленого програвача. Старі архіви випусків та історична ревізія CLI з інструкції встановлення не отримують ці функції автоматично. Встановлюйте **всі файли `cli/*.py` разом**, зокрема `preset_session.py`; зберігайте приватну конфігурацію.

## Увімкнення обмеженого довготривалого збереження результатів

Додайте цей необов’язковий блок до приватної конфігурації сервера, перевірте її та перезапустіть сервер. Виберіть абсолютний шлях на локальній постійній файловій системі, доступний для запису обліковому запису служби. В Unix каталог має бути приватним (0700); наявні файли журналу та блокування мають бути звичайними приватними файлами (0600). У Windows обмежте ACL каталогу обліковим записом служби. Одним журналом володіє один процес.

```json
"journal": {
  "path": "/var/lib/ottplay-control/private/operations.json",
  "max_records": 1024,
  "retention_seconds": 86400
}
```

Сервер створює відсутні каталоги з режимом 0700. Межі: 1–4096 записів, 60–86400 секунд і 4 MiB на диску. Термін збереження має охоплювати `command_ttl_seconds`. Заповнений журнал відхиляє нові операції з ключами, а не витісняє чинні записи. Пошкоджені файли, незахищений каталог Unix, інший процес запису або невдалий довготривалий запис призводять до безпечної відмови. Типовим залишається наявний шлях команд у пам’яті.

Комплектний модуль systemd створює `/var/lib/ottplay-control` з режимом 0700. Для Compose підготуйте каталог хоста, що належить UID 65532, задайте його абсолютний шлях у `CONTROL_SERVER_STATE` і поєднайте `deploy/compose.yml` з `deploy/compose.journal.yml`. Другий файл додає лише доступне для запису монтування стану; коренева файлова система залишається лише для читання. Для Helm окремо підготуйте запит постійного тому та задайте `journalExistingClaim=CLAIM_NAME`. Він монтується в `/var/lib/ottplay-control`; використовуйте показаний вище приватний підкаталог. Chart зберігає одну репліку, `Recreate` та `fsGroupChangePolicy: OnRootMismatch`, щоб повторне монтування не розширювало рекурсивно права вже створених приватних каталогів. Перевірте, що обраний драйвер сховища підтримує таку семантику власності. Chart не створює й не видаляє запит, а ввімкнення монтування не вмикає журнал: це й надалі визначає приватна конфігурація сервера.

Для `POST /api/requests` додайте `idempotency_key` поряд з `action` і `params`. Старі POST команд натомість приймають `Idempotency-Key`. Ключі містять 16–80 ASCII-літер, цифр, підкреслень або дефісів; створюйте новий випадковий ключ для кожного наміру. Той самий власник/ключ із тим самим пристроєм, дією та нормалізованим JSON-вмістом повертає початковий ID без повторного додавання до черги. Зміна вмісту повертає 409. Ключі обмежені ID оператора (або адміністратором), а не пристроєм. Після завершення терміну збереження ключ може бути прийнятий як новий намір: клієнти не повинні повторювати старий намір поза цим вікном.

`GET /api/operations?device_id=DEVICE` повідомляє, чи ввімкнено журнал, його межі та TTL команд. Додайте `&key=KEY`, щоб прочитати операцію:

- `pending`: прийнято; збереженої відповіді ще немає.
- `responded`: надійшла перевірена відповідь програвача; `result_status` дорівнює `ok`, `rejected` або `unsupported`. Початковий вміст результату й далі закінчує термін дії як звичайно.
- `acknowledged`: старий споживач підтвердив команду. Це не доводить видиме відтворення чи збереження зміни налаштувань.
- `unknown`: минув граничний термін або сервер перезапустився до збереження відповіді. Після перезапуску сервер **ніколи не повторює** цю команду.

Повторний POST із ключем повертає `status: retained`, початковий ID та стан. Звичайні нові POST зберігають `status: queued`. Записи журналу містять лише власника, пристрій, дію, випадкові ID, хеш вмісту, стан і граничні терміни. Вони не містять вмісту команд, URL провайдерів, токенів, знімків екрана чи тіл відповідей. Команди, що очікують, не зберігаються постійно. Це обмежена дедуплікація та відстеження результатів, а не виконання рівно один раз, довготривала черга роботи чи висока доступність кількох серверів.

## Планування, застосування, продовження та перевірка Local/Home

Наявна поведінка `ott PLAYER load PRESET` зберігається. Для нового процесу:

```sh
ott tv load Local plan
ott tv load Local apply
ott tv load Local resume
ott tv load Local verify
```

`plan` працює офлайн: перевіряє локальний пресет і перелічує слоти налаштувань та бажаний активний профіль, не друкуючи їхній вміст. Програвач не перевіряється. `verify` виконує точні порівняння лише для читання та перевіряє вибраний профіль M3U. За відмінностей або непідтримуваного порівняння повертається ненульовий код.

`apply` потребує журналу сервера. Він створює приватну контрольну точку та порівнює кожного налаштованого провайдера перед першою зміною. Кожне збереження порівнює збережені байти з очікуваними значеннями через `settings_compare`; збіг пропускає запис. Фінальна перевірка охоплює Plex, усі слоти M3U, необов’язкові слоти Stalker і вибраний профіль M3U. Порівняння повертають логічне значення, ніколи не збережені секрети.

Типова контрольна точка розміщується в `~/.config/ottplay-control/checkpoints/`. Використовуйте `--checkpoint /absolute/private/path/session.json` після режиму, щоб вибрати інший файл. Контрольні точки містять пристрій, назву пресета, хеш ревізії сервера/пресета, назви завершених кроків та один випадковий ключ операції, що очікує, з її терміном. Значень налаштувань вони не містять. Файли атомарно замінюються після fsync і блокуються від одночасних записів CLI. Зберігайте відповідний локальний пресет доступним. В Unix каталог має бути приватним (0700), зі звичайними файлами в режимі 0600. У Windows обмежте успадковану ACL каталогу користувачем, який запускає CLI; біти режиму Unix не забезпечують права доступу Windows.

`resume` перевіряє той самий сервер, пристрій і ревізію пресета, а потім читає очікуваний результат. Збережена відповідь дозволяє негайну повторну перевірку. Невизначений результат зупиняє надсилання змін, доки не минуть термін попередньої команди, тайм-аут запиту та невеликий запас. Після цього вікна знову запустіть `resume`. Він повторно перевіряє збережені налаштування навіть завершених кроків, щоб не прийняти зміни користувача за успішні попередні записи. Він ніколи не повторює відносну команду наосліп. Абсолютний вибір провайдера/профілю можна повторити після захисної паузи.

Новий `apply` ніколи не перезаписує наявну контрольну точку. Використайте її повторно через `resume` або виберіть новий файл для зміненого пресета. Окремі пристрої мають окремі контрольні точки. Немає транзакції чи відкочування, що охоплює всі програвачі; успішні попередні записи залишаються, якщо пізніший крок завершується помилкою. `verified` підтверджує збережені значення програвача в момент порівняння, а не успішне мережеве завантаження чи фізичне відтворення відео/аудіо.

## Надавайте інтеграціям лише потрібні повноваження

Для HA, RF-моста чи агента використовуйте [звичайних операторів команд](security-design.md#scoped-command-operators) замість розповсюдження `admin_token`. Дозволяйте точні ID пристроїв та операції на кшталт `input.channel_up` і `input.channel_down`. Для цього процесу пресетів операції налаштувань потребують явних дозволів `settings_compare`, `provider`, `profiles`, `status`, `profile`, `profile_settings` і `provider_settings`. Передавання потребує `playback_handoff_export` на джерелі та `playback_handoff_import` на цілі. Запис оператора поєднує зазначені пристрої та дії; використовуйте окремі ідентичності, якщо та сама операція не повинна застосовуватися до кожного переліченого пристрою. Токени та згода на діагностику залишаються окремими повноваженнями.

Оператори не можуть опитувати черги програвачів, надсилати відповіді програвачів, перелічувати всі пристрої, читати налагоджувальний вивід адміністратора чи результат іншого оператора. Звуження дозволеної дії також забороняє читання її збереженої операції. Видалення оператора та перезапуск відкликають його облікові дані. Не використовуйте ID оператора для іншого суб’єкта, поки залишаються старі записи журналу.

## Продовження на іншому програвачі

```sh
ott handoff living-room bedroom
```

Джерело експортує посилання на прямий ефір/архів версії 1: провайдера, непрозору ідентичність джерела, непрозорий відбиток елемента `channel-v1:<8 hex>.<8 hex>` і для архіву — поточний час програми. Сирі ID провайдерів та URL потоків залишаються локальними. Ціль повинна мати **те саме налаштоване джерело/обліковий запис**, знайти єдиний відповідний елемент у власному каталозі й отримати свіжий URL за власними локальними обліковими даними. Контролер не копіює придатний для відтворення URL і не змінює облікові дані цілі. Джерело продовжує відтворення. Успішний результат CLI означає, що ціль надіслала запит, а не що її фізичний екран чи динаміки перевірено.

Версія 1 підтримує каталоги ефіру/архіву `m3u`, `xtream` і `stalker`, якщо програвач може надати потрібні ідентичності. Невідомі чи неоднозначні елементи, невідповідні джерела й відмова локальної політики спричиняють помилку без запасного пошуку за назвою. VOD/серіали, зіставлення різних облікових записів, призупинення джерела та безперервна синхронізація історії/обраного не входять до цього першого контракту.

## Перевірки та вправи з відновлення

Запустіть `go test -race ./...`, `go vet ./...` і `python3 -m unittest discover -s tests`. Тести охоплюють втрачені відповіді після успішного запису, точне порівняння перед продовженням, відхилення конфігурації, терміни невідомих операцій, двох процесів запису, пошкоджені журнали, читання між операторами та некоректні дані передавання. На тестовому програвачі додатково перервіть CLI після збереження налаштування, перезапустіть контролер, продовжте й перевірте; протестуйте передавання між відповідними та невідповідними джерелами. Відео/аудіо підтвердьте окремо.

Для локальної перевірки між репозиторіями з поточною робочою копією FOSS і встановленими залежностями розробки виконайте:

```sh
node scripts/smoke_foss_roadmap.cjs /path/to/ottplay-foss
```

Димовий тест збирає цей Go-сервер, компілює весь TypeScript-проєкт FOSS і запускає його реальний транспорт, обробники команд, ідентичність джерела та комплектний кодек списків відтворення проти Python CLI. Він перевіряє точні налаштування всіх трьох підтримуваних провайдерів, невідповідності, передавання ефіру з різними локальними ID рядків, зміщення пошуку в архіві, невдале отримання URL і сувору валідацію формату передавання. Лише сховище, політика провайдера й інтерфейси хоста відтворення є тестовими підмінами; браузер, фізичний медіавивід чи реальний доступ до облікового запису не перевіряються. Він слухає loopback, використовує приватні тимчасові файли, не звертається до URL потоків і видаляє свої файли/сервер після завершення.
