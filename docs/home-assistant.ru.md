# События Home Assistant на активных проигрывателях

[English и полный справочник полей](home-assistant.md) · [CLI](cli.md) · [Развёртывание](deployment.md)

Контроллер OTT-play подключается к Home Assistant по WebSocket с long-lived
access token и превращает выбранные события в короткие текстовые баннеры.
Токен HA остаётся на контроллере. Проигрыватели используют свои существующие
ключи удалённого управления.

Нужны версии **контроллера и проигрывателя**, содержащие эту интеграцию.
Обновление сервера не добавляет её старой странице телевизора или установленному
приложению. Общий код работает в браузере, LG, Tauri и Capacitor; нативное
приложение нужно обновить пакетом с новым кодом проигрывателя. Инструкция ниже
описывает реализацию и порядок приёмки, а не подтверждает проверку всех устройств.

![Архитектура: HA, контроллер с фильтрами и активные проигрыватели](assets/home-assistant-architecture.svg)

## Как это работает

1. Сервер авторизуется в HA и подтверждает подписку на явно заданные типы событий.
2. Правила выбирают сущности и переходы состояний, применяют ограничение частоты
   и формируют обычный текст. HTML, скрипты и команды из события не выполняются.
3. Баннер попадает в отдельную очередь конкретного активного проигрывателя.
   Обновлённые проигрыватели опрашивают `/api/notifications` примерно раз в 5 секунд.
4. Перед показом проигрыватель проверяет свою активность. Standby, скрытая вкладка,
   фоновое приложение исключают показ; Android дополнительно использует состояние
   Activity и экрана. Уведомление не запускает поток и не будит устройство.

Очередь хранится только в памяти: максимум 4 баннера на устройство, срок доставки
по умолчанию 15 секунд. Активность устаревает через 15 секунд без опроса. Смена
runtime, уход в standby и устаревание активности сбрасывают старые сообщения.
После `go` или восстановления связи история не проигрывается.

## Токен и разрешения HA

Откройте в HA профиль пользователя → **Security → Long-lived access tokens** и
создайте токен контроллера. Сохраните его сразу: повторно HA его не показывает.
Удобно завести отдельную учётную запись. Токен наследует её права; он не является
отдельным read-only ключом. Большинство пользовательских типов событий требуют
прав администратора HA. Это описано в документации
[токенов](https://contributors.home-assistant.io/core/internals/auth-api/#long-lived-access-tokens)
и [подписок](https://contributors.home-assistant.io/core/internals/websocket-api/#subscribe-to-events).

Храните токен отдельным приватным файлом вне Git, например
`~/.config/ottplay-control-server/ha-token`. В файле — только токен; завершающий
перевод строки допустим. Для создания без попадания токена в историю команд
используйте [интерактивный Python-пример](home-assistant.md#1-create-and-store-the-ha-token).
На Unix права файла — `0600` для своего процесса; контейнеру предоставьте чтение
его пользователю/группе. В Windows ограничьте ACL служебной учётной записью.

В JSON нужен абсолютный путь: `~` и переменные окружения не раскрываются.
Не помещайте токен в URL, настройки проигрывателя, аргументы команд или отчёты.

## Конфигурация с примерами

Добавьте объект `home_assistant` в **существующий** приватный `config.json`,
сохранив зарегистрированные устройства и их ключи. Это фрагмент, а не полный
конфигурационный файл:

```json
{
  "home_assistant": {
    "enabled": true,
    "url": "https://ha.example.net",
    "token_file": "/absolute/private/path/ha-token",
    "max_per_minute": 30,
    "event_max_age_seconds": 30,
    "rules": [
      {
        "id": "home-announcement",
        "event_type": "ottplay_notification",
        "title": "{{title}}",
        "message": "{{message}}",
        "severity": "info",
        "duration_ms": 5000,
        "ttl_seconds": 15,
        "cooldown_seconds": 5
      },
      {
        "id": "door-open",
        "event_type": "state_changed",
        "entity_ids": ["binary_sensor.front_door"],
        "from": ["off"],
        "to": ["on"],
        "title": "Входная дверь",
        "message": "{{name}} открыта",
        "severity": "warning",
        "duration_ms": 7000,
        "ttl_seconds": 15,
        "cooldown_seconds": 60,
        "targets": ["living-room"]
      }
    ]
  }
}
```

`targets` содержит **ID регистрации на сервере**, видимые в `ott devices`.
Короткие локальные имена CLI вроде `l`, `t1` не подставляются автоматически.
Без `targets` или с `[]` правило адресуется всем подходящим активным устройствам.
Первое правило выше рассылает сообщения всем, второе — только `living-room`.

`url` — HTTP(S)-адрес HA без credentials/query/fragment. Например,
`https://example.net/ha/` превращается в `wss://example.net/ha/api/websocket`.
Прокси должен пропускать WebSocket upgrade, сертификат — быть доверенным для
процесса контроллера. Нужен маршрут от сервера к HA, а не от телевизора к HA.

Основные ограничения:

- 1–64 правила с уникальным `id`; только явно указанные `event_type`.
- Для `state_changed` обязательны 1–128 точных `entity_ids`. `from` и `to`
  необязательны, до 16 состояний в каждом. Изменение одних атрибутов, создание
  или удаление сущности не создаёт баннер перехода состояния.
- Подстановки: `{{entity_id}}`, `{{name}}`, `{{old_state}}`, `{{state}}`,
  `{{event_type}}`, `{{title}}`, `{{message}}`. Это не Jinja. Для пользовательского
  события используются только строки `event_data.title` и `event_data.message`.
  Пустой итоговый заголовок или текст означает пропуск уведомления.
- Заголовок — до 120, текст — до 512 единиц UTF-16. Emoji обычно занимает две.
  Управляющие символы удаляются; длинный подставленный текст ограничивается.
- `severity`: `info`, `warning`, `critical`; по умолчанию `info`.
- `duration_ms`: 1000–15000, по умолчанию 5000. `ttl_seconds`: 1–60,
  по умолчанию 15. Продолжительность показа не продлевает ожидание доставки.
- `cooldown_seconds`: 1–86400, по умолчанию 60 на правило и сущность.
  Пользовательское событие имеет общий cooldown своего правила.
- `max_per_minute`: 1–120, по умолчанию 30. `event_max_age_seconds`: 1–300,
  по умолчанию 30. Ноль выбирает значение по умолчанию, а не снимает ограничение.
- События без времени, слишком старые или более чем на 5 секунд из будущего
  отбрасываются. Синхронизируйте часы HA и контроллера.

Для сложных условий, порогов и расписания используйте автоматизацию в HA,
которая создаёт `ottplay_notification` с уже готовым текстом.

### Готовый набор: движение, присутствие, свет и розетки

В HA откройте **Developer tools → States** и уточните реальные ID и сырые
состояния сущностей. Интерфейс может показывать «Обнаружено» или «Занято», хотя
сырое значение — `on`. Выбирайте `binary_sensor` по назначению: прекращение
движения не означает, что в комнате никого нет. Для присутствия используйте
отдельный датчик занятости комнаты. Обнаружение движения уведомляет;
переход движения в `off` намеренно игнорируется.

Добавьте эти записи в `home_assistant.rules`, заменив примерные ID своими.
Свет и розетки выбраны явно: не каждый `switch` является розеткой — это также
может быть реле, приватность камеры или другая функция. Укажите только
проверенные розетки. Без `targets` сообщение получают все подходящие активные
плееры; для ограничения добавьте в каждое правило точные ID регистраций.

```json
{
  "rules": [
    {
      "id": "motion-detected", "event_type": "state_changed",
      "entity_ids": ["binary_sensor.hall_motion"],
      "from": ["off"], "to": ["on"],
      "title": "Движение", "message": "{{name}}: обнаружено движение",
      "cooldown_seconds": 10
    },
    {
      "id": "room-occupied", "event_type": "state_changed",
      "entity_ids": ["binary_sensor.living_room_occupancy"],
      "from": ["off"], "to": ["on"],
      "title": "Присутствие", "message": "{{name}}: комната занята",
      "cooldown_seconds": 10
    },
    {
      "id": "room-clear", "event_type": "state_changed",
      "entity_ids": ["binary_sensor.living_room_occupancy"],
      "from": ["on"], "to": ["off"],
      "title": "Присутствие", "message": "{{name}}: комната свободна",
      "cooldown_seconds": 10
    },
    {
      "id": "lights-on", "event_type": "state_changed",
      "entity_ids": ["light.living_room", "light.hall"],
      "from": ["off"], "to": ["on"],
      "title": "Свет", "message": "{{name}}: включено",
      "cooldown_seconds": 2
    },
    {
      "id": "lights-off", "event_type": "state_changed",
      "entity_ids": ["light.living_room", "light.hall"],
      "from": ["on"], "to": ["off"],
      "title": "Свет", "message": "{{name}}: выключено",
      "cooldown_seconds": 2
    },
    {
      "id": "outlets-on", "event_type": "state_changed",
      "entity_ids": ["switch.desk_outlet", "switch.floor_lamp_outlet"],
      "from": ["off"], "to": ["on"],
      "title": "Розетки", "message": "{{name}}: включено",
      "cooldown_seconds": 2
    },
    {
      "id": "outlets-off", "event_type": "state_changed",
      "entity_ids": ["switch.desk_outlet", "switch.floor_lamp_outlet"],
      "from": ["on"], "to": ["off"],
      "title": "Розетки", "message": "{{name}}: выключено",
      "cooldown_seconds": 2
    }
  ]
}
```

Для присутствия, света и розеток включение и выключение имеют разные ID правил: cooldown включения не подавляет
следующее выключение. Общий лимит частоты, границы очереди, проверка активности
и cooldown повторного перехода в ту же сторону продолжают действовать.
Явные `from` и `to` исключают переходы через `unknown` / `unavailable` и
инициализацию датчика. Восстановление связи с лампой не будет выдано за включение
из неизвестного состояния. Изменение только яркости при состоянии `on` молчит.
Удалите пересекающееся правило для той же сущности и перехода, если второй
баннер не нужен. Уведомление сообщает состояние, а не устанавливает, кто или что
его изменило.

## Сборка, запуск и установка

Установите релиз с интеграцией либо соберите текущий код Go-инструментарием,
указанным в `go.mod`:

```sh
go build -trimpath -o ./ottplay-control-server ./cmd/ottplay-control-server
./ottplay-control-server version
# Только для новой установки, существующий файл не перезаписывается:
./ottplay-control-server init --config "$HOME/.config/ottplay-control-server/config.json" --device-id living-room
# После редактирования конфигурации:
./ottplay-control-server validate --config "$HOME/.config/ottplay-control-server/config.json"
./ottplay-control-server serve --config "$HOME/.config/ottplay-control-server/config.json"
```

Каталог конфигурации должен существовать. `validate` проверяет структуру,
но не подтверждает живое подключение HA. Для установленного сервиса используйте
[инструкцию развёртывания](deployment.md). Изменение правил требует перезапуска
контроллера; `ott l restart` перезапускает только проигрыватель.

Обновите все модули CLI одной версией, затем:

```sh
ott ha status
ott ha status -j
ott devices
ott l
```

Последняя команда использует ваш локальный псевдоним проигрывателя. Включите на
нём Remote control и установите актуальный frontend. Для Tauri/Capacitor нужна
новая установленная сборка; для here.now — обновлённая публикация и её загрузка.

### Docker и Helm

Образ работает как UID/GID `65532`; предоставьте ему чтение файла токена, не
делая файл общедоступным. В Compose добавьте read-only bind mount в
`/run/secrets/ha-token`, а в JSON задайте тот же `token_file`.
Полный [Compose override и команды](home-assistant.md#docker-compose) приведены
в основном руководстве. После атомарной замены bind-mounted файла контейнер
нужно пересоздать, чтобы он увидел новый inode.

Helm chart уже монтирует все ключи `existingSecret` в
`/etc/ottplay-control-server` с правами `0440` и группой `65532`. Добавьте ключ
`ha-token` рядом с `config.json`; путь в конфигурации:
`/etc/ottplay-control-server/ha-token`. Пример для новой Secret:

```sh
kubectl -n ottplay create secret generic ottplay-control-server-ha \
  --from-file=config.json=/absolute/private/path/config.json \
  --from-file=ha-token=/absolute/private/path/ha-token
helm upgrade --install ottplay-control-server ./charts/ottplay-control-server \
  --namespace ottplay \
  --set existingSecret=ottplay-control-server-ha \
  --set-string image.tag=REPLACE_WITH_PUBLISHED_TAG
kubectl -n ottplay rollout status deployment/ottplay-control-server
```

Namespace должен существовать. Подставьте опубликованный тег с интеграцией,
свой namespace/release и полный конфигурационный файл. Сохраняйте одну реплику:
очереди и состояние моста находятся в памяти конкретного процесса.

## Событие и автоматизация в HA

Создайте скрипт в YAML-редакторе HA:

```yaml
alias: Проверка баннера OTT-play
mode: single
sequence:
  - event: ottplay_notification
    event_data:
      title: "Дом"
      message: "Ужин готов"
```

Либо в **Developer tools → Events** отправьте событие `ottplay_notification`
с данными `title` и `message`. Текст должен появиться на активном проигрывателе
после его очередного опроса. Повторяйте проверку с интервалом больше cooldown.

Пример автоматизации, которую следует привязать к вашей реальной сущности:

```yaml
alias: Стирка завершена — уведомить OTT-play
triggers:
  - trigger: state
    entity_id: sensor.washing_machine_status
    from: "running"
    to: "finished"
actions:
  - event: ottplay_notification
    event_data:
      title: "Стирка"
      message: "Стиральная машина закончила работу"
mode: single
```

ID и строки состояния в примере условные. Фильтры `targets`, важность и длительность
задаются правилом контроллера; дополнительные поля события не управляют плеером.
Синтаксис действия описан в [документации HA](https://www.home-assistant.io/actions/event/).

## Статус и правильная приёмка

![Жизненный цикл события, фильтры, восстановление связи и истечение срока](assets/home-assistant-lifecycle.svg)

`ott ha status` использует `GET /api/home-assistant/status`. Администратор видит
состояние моста, активность устройств и счётчики `queued`, `polled`, `skipped`,
`dropped`. Оператор команд с разрешением `status` видит только разрешённые ему
устройства и поля моста `enabled`, `state`, `last_error_code`; глобальные счётчики
моста и `delivery` ему не выдаются. Ответ не содержит токен, URL HA или тексты
событий. Счётчики сбрасываются с перезапуском процесса.

`connected` подтверждает авторизацию и подписки. `events_matched` означает
совпадение хотя бы с одним правилом, даже если cooldown остановил отправку.
`notifications_queued` / `queued` означает постановку в очередь; `polled` —
получение проигрывателем. **Ни один из этих счётчиков не подтверждает показ на
экране.** Проверьте экран или доступный адаптер скриншотов.

Для воспроизводимой локальной проверки есть
`scripts/smoke_home_assistant.cjs`: настоящий контроллер, локальный имитатор HA,
собранный player в headless Chromium и CLI. Используются тестовые ключи,
внешние запросы браузера блокируются. Реальный HA и устройства не нужны:

```sh
# В checkout ottplay-foss соответствующей версии:
npm ci
npm run build
npx playwright install chromium
# В checkout ottplay-control-server:
node scripts/smoke_home_assistant.cjs /absolute/path/to/ottplay-foss
```

Нужны Node.js, Python 3.12 или новее для CLI, Go из `go.mod`, Playwright в checkout проигрывателя и готовые
`dist/index.html` / `dist/player.js`. Проверяются буквальная отрисовка текста,
очистка в standby, пропуск для неактивного плеера, отсутствие старого сообщения
после `go`, новое сообщение после пробуждения и безопасные счётчики CLI.
Этот тест не подтверждает видимость поверх нативного видео на физическом устройстве.

Порядок живой проверки:

1. Запишите версии сервера, CLI и установленного проигрывателя. Откройте
   `ott ha status`, затем отправьте безвредное тестовое событие.
2. Убедитесь, что баннер виден, поток продолжает идти и провайдер не изменился.
3. Проверьте правило с единственным ID: второй активный плеер его не показывает.
4. Выполните `ott l standby`, отправьте новое событие, затем `ott l go`.
   Старого баннера быть не должно. Повторите со скрытой вкладкой и нативным фоном.
5. Прервите и восстановите маршрут контроллера к HA. Проверьте reconnect,
   отсутствие воспроизведения старой истории и доставку нового события.
6. Повторите на каждом реально установленном типе плеера, отдельно записав результат.

Браузерная видимость не определяет присутствие человека и не всегда знает,
выключен ли внешний монитор. Android использует дополнительные нативные сигналы
экрана/Activity; Tauri, iOS и LG пока опираются на видимость документа и standby.
Физическое состояние их экрана этим не подтверждается. Уведомления имеют best-effort доставку;
не используйте их единственным каналом критически важных сигналов.

Общий overlay показывает до трёх текстовых баннеров с цветной рамкой важности,
не меняет фокус, не содержит действий и работает в strict kiosk. Отрисовку поверх
нативной видеоповерхности проверяйте на самом устройстве. Отдельного признака
в `caps` пока нет: проверяйте установленную сборку, активность в `ott ha status`
и реальное тестовое событие.

Адрес и токен HA эта доработка не подставляет. Для живого теста задайте их
приватно; извлекать токен из зашифрованного хранилища Desktop не требуется.
Desktop использован как образец подключения. Локальный сервер без настройки
интеграции должен показывать `disabled`.

## Диагностика и восстановление

- **Неизвестная команда / HTTP 404:** проверьте реальный CLI launcher и запущенный
  сервер, обновите обе установки. Затем отдельно обновите проигрыватель.
- **`disabled`:** проверьте `enabled` в файле именно работающего сервиса, выполните
  `validate` и перезапуск контроллера.
- **`token_error`:** файл отсутствует, не читается UID/GID процесса или не содержит
  корректной строки токена. Проверьте абсолютный путь и mount.
- **`auth_failed`:** HA отклонил токен. Проверьте HA-аккаунт. Повторно один и тот же отклонённый токен не
  отправляется; содержимое файла проверяется каждые 5 секунд.
- **`reconnecting` с `subscription_rejected`:** авторизация прошла, но подписка
  отклонена; проверьте права аккаунта для выбранных типов событий.
- **`reconnecting`:** проверьте DNS, VPN, порт, доверие сертификату и WebSocket
  upgrade прокси. При сетевых сбоях пауза растёт от 1 до 30 секунд с небольшим
  случайным добавлением. Ping — каждые 20 секунд, ожидание pong — 10 секунд.
  Мост подключается напрямую и не использует `HTTP_PROXY` / `HTTPS_PROXY`;
  нужен прямой маршрут либо явно заданный адрес reverse proxy перед HA.
- **Связь есть, совпадений нет:** проверьте точные entity ID, `on/off`, `from/to`,
  cooldown, время события и синхронизацию часов. MQTT-соединение HA/Frigate
  независимо от используемого здесь WebSocket.
- **Совпадение есть, баннера нет:** проверьте ID назначения, активность, поддержку
  уведомлений сборкой, CORS и маршрут `/api/notifications`. После пробуждения
  отправьте новое событие; старое намеренно не воспроизводится.
- **Повторы:** исключите пересекающиеся правила и несколько экземпляров сервера,
  сузьте фильтры или увеличьте cooldown.

### Ротация токена

Создайте новый токен, безопасно замените приватный файл, перезапустите контроллер
и проверьте статус плюс новое тестовое событие. После успешной проверки отзовите
старый токен в HA. Если он скомпрометирован, отзовите немедленно, допустив короткий
перерыв. Активный WebSocket не переавторизуется только от изменения файла:
нужен reconnect/restart. Для уже отклонённого токена изменение файла обнаружится
при очередной пятисекундной проверке.

Для Docker пересоздайте контейнер после замены bind-mounted файла; для Kubernetes
обновите Secret и выполните rollout restart своего deployment. Тексты токенов
не выводите в терминал или отчёт.

### Отключение и откат

Установите `home_assistant.enabled: false` и перезапустите контроллер.
Обычные remote-команды и регистрации останутся доступны. Для полного отзыва
интеграции отзовите HA-токен и уберите его mount. Перед откатом на сервер без
этой функции удалите объект `home_assistant` из его конфигурации и выполните
`validate` старым бинарником. Сохраните приватную копию рабочей конфигурации.

В отчёт о неисправности включайте версии, ID правил/устройств, безопасный статус,
UTC-время события и наблюдение экрана. Не прикладывайте токены, полные приватные
конфигурации или сырые события домашней автоматики.

## Приватный кадр камеры при движении

![Приватная доставка кадра](assets/home-assistant-camera.svg)

К событию обнаружения движения можно добавить один JPEG. Он не запускает
второй видеоплеер или звук камеры. Единый выключатель уведомлений на экземпляре
плеера относится и к тексту, и к изображению; remote control продолжает работать.
События окончания движения не добавляйте. Выключения света, розеток и occupancy
могут оставаться отдельными правилами.

Полная схема `cameras` → `camera_key`, пример правила, ограничения и порядок
отката приведены в [разделе camera snapshots](home-assistant.md#private-camera-motion-snapshots).
Используется уже существующее событие `cisco_motion_snapshot_requested` с
`camera_key`, `event_id`, `event_at`. Ключ сопоставляется только с явно разрешённой
HA-камерой; URL из события не используются. Исходное время допускает до 90 секунд
прогрева камеры, внешнее событие по-прежнему ограничено обычными 30 секундами.

Без активного получателя с поддержкой JPEG сервер не обращается к камере.
При ошибке захвата остаётся текст. Кадр ограничен 640×360 / 160 KiB и хранится
только в памяти до исходного срока уведомления. Получение требует device Bearer
и совпадающей активной сессии; публичных URL и HA-токенов в плеере нет.
`camera_acquired`, `camera_failed`, `camera_skipped` помогают диагностике,
но не подтверждают отображение на физическом экране. Не прикладывайте кадры,
base64 или приватные конфигурации к отчётам.

Команды единого выключателя, включая группы плееров, описаны в
[notification preferences](notification-preferences.md).
