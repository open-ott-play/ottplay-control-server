# Надёжное управление и перенос просмотра

[English](reliable-control.md) · [Русский](reliable-control.ru.md) · [Оглавление](wiki/Home.ru.md)

Нужны контроллер и CLI из версии, содержащей это руководство. Точное сравнение
настроек и перенос просмотра также требуют обновлённого плеера. Старые архивы
и зафиксированная историческая версия CLI из инструкции установки не получают
эти функции автоматически. Устанавливайте все файлы `cli/*.py` одной версии,
включая `preset_session.py`, сохраняя приватную конфигурацию отдельно.

## Журнал результатов с ограниченным размером

Добавьте необязательный блок в приватную конфигурацию сервера, проверьте её
командой `validate` и перезапустите сервер:

```json
"journal": {
  "path": "/var/lib/ottplay-control/private/operations.json",
  "max_records": 1024,
  "retention_seconds": 86400
}
```

Выберите абсолютный путь на постоянной локальной файловой системе. В Unix
каталог должен иметь права 0700, существующие обычные файлы журнала и блокировки
— 0600. Отсутствующие каталоги создаются с правами 0700. В Windows ограничьте ACL
учётной записью сервиса. Одновременно журналом владеет один процесс.

Допустимы 1–4096 записей, срок 60–86400 секунд, размер до 4 МиБ. Срок хранения
должен быть не меньше `command_ttl_seconds`. Заполненный журнал отклоняет новые
операции с ключом, а не удаляет действующие записи. Повреждённый журнал,
небезопасные права Unix, второй процесс или ошибка сохранения приводят к отказу.
Без настройки сохраняется прежняя очередь в памяти.

Штатный systemd unit создаёт `/var/lib/ottplay-control` с правами 0700. Для
Compose подготовьте каталог владельца UID 65532, задайте абсолютный
`CONTROL_SERVER_STATE` и объедините `deploy/compose.yml` с
`deploy/compose.journal.yml`. Корневая файловая система остаётся только для
чтения. Для Helm отдельно создайте постоянный PVC и задайте
`journalExistingClaim=ИМЯ_PVC`: он монтируется в `/var/lib/ottplay-control`, а
журнал использует приватный подкаталог из примера. Сохраняются одна реплика,
`Recreate` и `fsGroupChangePolicy: OnRootMismatch`, чтобы повторное подключение
не расширяло права вложенных каталогов. Проверьте поддержку этих правил
владения выбранным драйвером хранилища. Chart не создаёт и не удаляет PVC;
журнал всё равно нужно включить в приватной конфигурации сервера.

В `POST /api/requests` добавляется `idempotency_key` рядом с `action` и `params`.
Старый командный POST принимает заголовок `Idempotency-Key`. Ключ — 16–80 ASCII
букв, цифр, `_` или `-`; генерируйте новый случайный ключ для каждого намерения.
Повтор того же ключа того же оператора с тем же устройством и нормализованным
JSON возвращает прежний ID без повторной постановки в очередь. Другие данные
дают 409. После срока хранения ключ может стать новой операцией: старые запросы
нельзя повторять за пределами этого окна.

`GET /api/operations?device_id=DEVICE` сообщает доступность, лимиты и TTL.
Добавьте `&key=KEY`, чтобы получить состояние:

- `pending` — запрос принят, сохранённого ответа ещё нет.
- `responded` — получен проверенный ответ плеера; `result_status` равен `ok`,
  `rejected` или `unsupported`. Полное тело ответа удаляется по обычному сроку.
- `acknowledged` — старый клиент подтвердил получение команды. Это не доказывает
  сохранение настройки или видимое воспроизведение.
- `unknown` — истёк срок команды либо сервер перезапустился до сохранения
  ответа. После перезапуска такая команда **не выполняется повторно**.

Повторный POST возвращает `status: retained`, прежний ID и состояние; новый —
`status: queued`. Журнал содержит владельца, устройство, действие, случайные ID,
хеш данных, состояние и сроки. URL провайдеров, токены, сами команды, снимки экрана
и тела ответов не сохраняются. Это ограниченное устранение дублей и учёт
результатов, а не гарантия однократного выполнения или постоянная очередь задач.

## Планирование, применение, продолжение и проверка Local/Home

Прежняя команда `ott PLAYER load PRESET` работает как раньше. Новый режим:

```sh
ott tv load Local plan
ott tv load Local apply
ott tv load Local resume
ott tv load Local verify
```

`plan` без сети проверяет локальный профиль и выводит номера слотов, требуемый
активный профиль и хеш версии, но не секретные значения. Текущее состояние плеера
эта команда не читает. `verify` сравнивает точные сохранённые значения и активный
M3U-профиль, ничего не изменяя. При несовпадении или отсутствии поддержки код
завершения ненулевой.

`apply` требует журнал сервера и создаёт приватную контрольную точку. До первой
записи проверяется поддержка сравнения всех провайдеров. Перед каждой записью
`settings_compare` сравнивает сохранённые байты с ожидаемыми; совпавшая запись
пропускается. Ответ содержит только логический результат. Итоговая проверка
охватывает Plex, все M3U-слоты, необязательные Stalker-слоты и активный M3U-профиль.

По умолчанию контрольные точки находятся в
`~/.config/ottplay-control/checkpoints/`. После режима можно указать
`--checkpoint /absolute/private/path/session.json`. Файл содержит устройство,
имя профиля, хеши адреса сервера и версии настроек, названия завершённых шагов,
один случайный ключ и срок неопределённой операции. Значений настроек в нём нет.
Запись выполняется атомарной заменой после fsync; параллельные CLI блокируются.

`resume` требует прежние сервер, устройство и версию профиля. Сохранённый ответ
сервера разрешает немедленную повторную проверку. При неопределённом исходе
изменения не отправляются до истечения TTL, тайм-аута запроса и небольшого запаса;
запустите `resume` снова после этого окна. Уже завершённые настройки тоже
сравниваются заново, поэтому внешнее изменение будет замечено. Относительные
команды вслепую не повторяются; абсолютный выбор провайдера/профиля может повторяться
после защитной проверки.

Новый `apply` не заменяет существующую контрольную точку. Используйте `resume`
или новый путь для изменённого профиля. Устройства независимы: общей транзакции
и отката для всех плееров нет. Ранее успешные записи сохраняются при последующей
ошибке. `verified` подтверждает настройки, а не загрузку источника или звук.

## Ограниченные полномочия интеграций

Для HA, RF-моста и агентов используйте [операторов команд](security-design.md#scoped-command-operators)
с точными устройствами и действиями вместо общего `admin_token`. Например,
`input.channel_up` и `input.channel_down`. Загрузка профиля требует разрешений
`settings_compare`, `provider`, `profiles`, `status`, `profile`,
`profile_settings`, `provider_settings`. Перенос просмотра требует
`playback_handoff_export` на исходном и `playback_handoff_import` на целевом плеере.
Одна запись оператора разрешает каждое перечисленное действие на каждом его
устройстве; для более узкого разделения используйте разные записи.

Оператор не может читать очереди плееров, отправлять ответы от их имени,
получать общий список устройств, административную отладку и чужие результаты.
Сужение списка действий также закрывает старые результаты этих действий.
Удаление оператора с перезапуском отзывает доступ. Не передавайте его ID другому
пользователю, пока в журнале хранятся старые записи. Диагностический доступ
остаётся отдельным механизмом.

## Продолжить просмотр на другом плеере

```sh
ott handoff living-room bedroom
```

Передаются провайдер, непрозрачная идентичность источника, отпечаток канала
`channel-v1:<8 hex>.<8 hex>` и текущее время программы для архива. Исходные ID
провайдера и URL потоков остаются в плеере. Целевой плеер должен иметь **тот же
настроенный источник/аккаунт** и единственный подходящий канал в своём каталоге.
Он сам получает свежий URL своими локальными реквизитами. Контроллер не копирует
URL потока и не меняет учётные данные. Исходный плеер продолжает работать.
Успех CLI подтверждает отправку воспроизведения, а не физический вывод.

Версия 1 поддерживает эфир и архив M3U/Xtream/Stalker при наличии необходимых
идентификаторов в плеере. Несовпадение источника, неоднозначность канала или
локальный запрет приводят к отказу без подбора по имени. VOD/сериалы, перенос
между разными аккаунтами, остановка исходного плеера и постоянная синхронизация
истории/избранного в этот контракт не входят.

## Проверки

Запустите `go test -race ./...`, `go vet ./...` и
`python3 -m unittest discover -s tests`. Проверяются потерянный ответ после записи,
продолжение без повторной записи, внешнее изменение настроек, неопределённый
исход, два процесса, повреждённый журнал, чужие результаты и неверный перенос.
На тестовом плеере дополнительно прервите CLI после записи, перезапустите сервер,
продолжите загрузку и выполните `verify`. Проверьте перенос между совпадающими
и различными источниками. Изображение и звук подтверждаются отдельно.

Для локальной проверки связки с актуальным FOSS и установленными зависимостями
разработки выполните:

```sh
node scripts/smoke_foss_roadmap.cjs /path/to/ottplay-foss
```

Тест собирает Go-сервер, компилирует весь TypeScript-проект FOSS и запускает
настоящий транспорт, обработчики команд, идентичность источника и поставляемый
кодек плейлиста через Python CLI. Проверяются точные настройки трёх провайдеров,
расхождения, перенос эфира при разных локальных ID, позиция архива, отказ
разрешения URL и строгая проверка протокола. Хранилище, политика провайдера и
вывод воспроизведения заменены тестовыми адаптерами; браузер, реальные аккаунты
и физическое изображение/звук этот тест не проверяет. Он использует loopback,
закрытые временные файлы, не обращается к URL потоков и удаляет свои файлы
и сервер после завершения.
