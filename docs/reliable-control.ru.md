Старые архивы релизов и историческая ревизия CLI из инструкции установки не получают эти функции автоматически. Устанавливайте **все файлы `cli/*.py` вместе**, включая `preset_session.py`; сохраняйте приватную конфигурацию.

## Включение ограниченного долговременного хранения результатов

Добавьте этот необязательный блок в приватную конфигурацию сервера, проверьте её и перезапустите сервер. Выберите абсолютный путь на локальной постоянной файловой системе, доступный для записи учётной записи службы. В Unix каталог должен быть приватным (0700); существующие файлы журнала и блокировки должны быть обычными приватными файлами (0600). В Windows ограничьте ACL каталога учётной записью службы. Одним журналом владеет один процесс.

```json
"journal": {
  "path": "/var/lib/ottplay-control/private/operations.json",
  "max_records": 1024,
  "retention_seconds": 86400
}
```

Сервер создаёт отсутствующие каталоги с режимом 0700. Ограничения: 1–4096 записей, 60–86400 секунд и 4 MiB на диске. Срок хранения должен покрывать `command_ttl_seconds`. Заполненный журнал отклоняет новые операции с ключом вместо вытеснения действующих записей. Повреждённые файлы, небезопасный каталог Unix, другой процесс записи или неудачная долговременная запись приводят к безопасному отказу. По умолчанию сохраняется существующий путь обработки команд в памяти.

Поставляемый модуль systemd создаёт `/var/lib/ottplay-control` с режимом 0700. Для Compose подготовьте каталог хоста, принадлежащий UID 65532, задайте его абсолютный путь в `CONTROL_SERVER_STATE` и объедините `deploy/compose.yml` с `deploy/compose.journal.yml`. Второй файл добавляет только доступное для записи монтирование состояния; корневая файловая система остаётся только для чтения. Для Helm отдельно подготовьте запрос постоянного тома и задайте `journalExistingClaim=CLAIM_NAME`. Том монтируется в `/var/lib/ottplay-control`; используйте показанный выше приватный подкаталог. Chart сохраняет одну реплику, `Recreate` и `fsGroupChangePolicy: OnRootMismatch`, чтобы повторное монтирование не расширяло рекурсивно права уже созданных приватных каталогов. Проверьте поддержку такой семантики владения выбранным драйвером хранилища. Chart не создаёт и не удаляет запрос, а включение монтирования не включает журнал: это по-прежнему задаётся приватной конфигурацией сервера.

Для `POST /api/requests` добавьте `idempotency_key` рядом с `action` и `params`. Старые POST команд вместо этого принимают `Idempotency-Key`. Ключи содержат 16–80 ASCII-букв, цифр, подчёркиваний или дефисов; создавайте новый случайный ключ для каждого намерения. Тот же владелец/ключ с тем же устройством, действием и нормализованным JSON-содержимым возвращает исходный ID без повторной постановки в очередь. Изменённое содержимое возвращает 409. Ключи ограничены ID оператора (или администратором), а не устройством. После истечения срока хранения ключ может приниматься как новое намерение: клиенты не должны повторять старое намерение за пределами этого окна.

`GET /api/operations?device_id=DEVICE` сообщает, включён ли журнал, его ограничения и TTL команд. Добавьте `&key=KEY`, чтобы прочитать операцию:

- `pending`: принято; сохранённого ответа пока нет.
- `responded`: поступил проверенный ответ плеера; `result_status` равен `ok`, `rejected` или `unsupported`. Исходное тело результата по-прежнему истекает обычным образом.
- `acknowledged`: старый потребитель подтвердил команду. Это не доказывает видимое воспроизведение или сохранение изменения настроек.
- `unknown`: истёк срок либо сервер перезапущен до сохранения ответа. Сервер **никогда не повторяет** эту команду после перезапуска.

Повторный POST с ключом возвращает `status: retained`, исходный ID и состояние. Обычные новые POST сохраняют `status: queued`. Записи журнала содержат только владельца, устройство, действие, случайные ID, хеш содержимого, состояние и сроки. Они не содержат данные команд, URL провайдеров, токены, скриншоты или тела ответов. Ожидающие команды не сохраняются долговременно. Это ограниченная дедупликация и отслеживание результатов, а не выполнение строго один раз, постоянная очередь работ или высокая доступность нескольких серверов.

## Планирование, применение, продолжение и проверка Local/Home

Существующее поведение `ott PLAYER load PRESET` сохраняется. Для нового процесса:

```sh
ott tv load Local plan
ott tv load Local apply
ott tv load Local resume
ott tv load Local verify
```

`plan` работает офлайн: проверяет локальный пресет и перечисляет слоты настроек и желаемый активный профиль, не выводя их содержимое. Плеер не проверяется. `verify` выполняет точные сравнения без записи и проверяет выбранный профиль M3U. При любом отличии или неподдерживаемом сравнении возвращает ненулевой код.

`apply` требует журнал сервера. Он создаёт приватную контрольную точку и сравнивает каждого настроенного провайдера до первого изменения. При каждом сохранении `settings_compare` сравнивает сохранённые байты с ожидаемыми значениями; совпадение пропускает запись. Итоговая проверка охватывает Plex, все слоты M3U, необязательные слоты Stalker и выбранный профиль M3U. Сравнения возвращают логическое значение, никогда не сохранённые секреты.

Контрольная точка по умолчанию находится в `~/.config/ottplay-control/checkpoints/`. Для другого файла используйте `--checkpoint /absolute/private/path/session.json` после режима. Контрольные точки содержат устройство, имя пресета, хеш ревизии сервера/пресета, названия завершённых шагов и один ожидающий случайный ключ операции с её сроком. Значений настроек в них нет. Файлы атомарно заменяются после fsync и блокируются от одновременной записи CLI. Сохраняйте соответствующий локальный пресет доступным. В Unix каталог должен быть приватным (0700), с обычными файлами в режиме 0600. В Windows ограничьте наследуемую ACL каталога пользователем, запускающим CLI; биты режима Unix не обеспечивают права доступа Windows.

`resume` проверяет тот же сервер, устройство и ревизию пресета, затем читает ожидающий результат. Сохранённый ответ разрешает немедленную повторную проверку. Неопределённый результат останавливает отправку изменений, пока не пройдут срок предыдущей команды, тайм-аут запроса и небольшой запас. После этого окна снова запустите `resume`. Сохранённые настройки проверяются повторно даже для завершённых шагов, чтобы не принять изменения пользователя за успешные прошлые записи. Относительная команда никогда не повторяется вслепую. Абсолютный выбор провайдера/профиля можно повторить после защитной паузы.

Новый `apply` никогда не перезаписывает существующую контрольную точку. Используйте её снова через `resume` либо выберите новый файл для изменённого пресета. У разных устройств отдельные контрольные точки. Нет общей транзакции или отката для всех плееров; успешные предыдущие записи сохраняются, если последующий шаг завершится ошибкой. `verified` подтверждает сохранённые значения плеера в момент сравнения, а не успешную загрузку по сети или физический вывод видео/аудио.

## Предоставляйте интеграциям только необходимые полномочия

Для HA, RF-моста или агента используйте [обычных операторов команд](security-design.md#scoped-command-operators) вместо распространения `admin_token`. Разрешайте точные ID устройств и операции вроде `input.channel_up` и `input.channel_down`. Операции настроек для этого процесса пресетов требуют явных разрешений `settings_compare`, `provider`, `profiles`, `status`, `profile`, `profile_settings` и `provider_settings`. Передаче нужны `playback_handoff_export` на источнике и `playback_handoff_import` на получателе. Запись оператора объединяет перечисленные устройства и действия; используйте отдельные идентичности, если одна операция не должна применяться ко всем указанным устройствам. Токены и согласие на диагностику остаются отдельными полномочиями.

Операторы не могут опрашивать очереди плееров, отправлять ответы плееров, перечислять все устройства, читать отладочный вывод администратора или результат другого оператора. Сужение области действия также запрещает чтение её сохранённой операции. Удаление оператора с перезапуском отзывает его учётные данные. Не используйте ID оператора для другого субъекта, пока сохраняются его старые записи журнала.

## Продолжение на другом плеере

```sh
ott handoff living-room bedroom
```

Источник экспортирует ссылку на эфир/архив версии 1: провайдера, непрозрачную идентичность источника, непрозрачный отпечаток элемента `channel-v1:<8 hex>.<8 hex>` и для архива — текущее время программы. Исходные ID провайдеров и URL потоков остаются локальными. Получатель должен иметь **тот же настроенный источник/аккаунт**, найти единственный соответствующий элемент в собственном каталоге и получить свежий URL со своими локальными учётными данными. Контролер не копирует воспроизводимый URL и не меняет учётные данные получателя. Источник продолжает воспроизведение. Успешный результат CLI означает отправку запроса получателем, а не проверку его физического экрана или динамиков.

Версия 1 поддерживает каталоги эфира/архива `m3u`, `xtream` и `stalker`, если плеер может предоставить нужные идентичности. Неизвестные или неоднозначные элементы, несовпадающие источники и отказ локальной политики завершаются ошибкой без запасного сопоставления по имени. VOD/сериалы, сопоставление разных аккаунтов, пауза источника и непрерывная синхронизация истории/избранного не входят в этот первый контракт.

## Проверки и упражнения по восстановлению

Запустите `go test -race ./...`, `go vet ./...` и `python3 -m unittest discover -s tests`. Тесты охватывают потерянные ответы после успешной записи, точное сравнение перед продолжением, расхождения конфигурации, сроки неизвестных операций, два процесса записи, повреждённые журналы, чтение между операторами и некорректные данные передачи. На тестовом плеере дополнительно прервите CLI после сохранения настройки, перезапустите контролер, продолжите и проверьте; испытайте передачу между совпадающими и несовпадающими источниками. Видео/аудио подтвердите отдельно.

Для локальной проверки между репозиториями с текущей рабочей копией FOSS и установленными зависимостями разработки выполните:

```sh
node scripts/smoke_foss_roadmap.cjs /path/to/ottplay-foss
```

Дымовой тест собирает этот Go-сервер, компилирует весь TypeScript-проект FOSS и запускает его настоящий транспорт, обработчики команд, идентичность источника и поставляемый кодек плейлистов против Python CLI. Он проверяет точные настройки всех трёх поддерживаемых провайдеров, расхождения, передачу эфира с разными локальными ID строк, смещения поиска в архиве, неудачное получение URL и строгую проверку формата передачи. Только хранилище, политика провайдера и интерфейсы хоста воспроизведения являются тестовыми подменами; браузер, физический вывод медиа и реальный доступ к аккаунтам не проверяются. Он слушает loopback, использует приватные временные файлы, не обращается к URL потоков и удаляет свои файлы/сервер при завершении.
