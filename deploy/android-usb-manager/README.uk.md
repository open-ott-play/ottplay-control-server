Цей каталог містить шаблони розгортання та [`Dockerfile`](Dockerfile) транспортного контейнера спільного менеджера. Менеджер на Python працює на USB-хості. Образ надає ADB, Python та інструменти адаптера атомарного обслуговування; він не містить другого реєстру пристроїв або демона відновлення. Підготовку, команди, міграцію, обмеження відновлення та відкат описано в [посібнику оператора](../../docs/android-usb-manager.md).

Без робочої копії Git завантажте `ottplay-control-server-deployment.tar.gz` і `release-manifest.json` з одного [випуску](https://github.com/open-ott-play/ottplay-control-server/releases). Перевірте дайджест архіву й розпакуйте його в новий каталог згідно з [отриманням пакета розгортання](../../docs/android-usb-manager.md#get-the-deployment-package). Пакет містить цей рецепт і шість локальних/віддалених скриптів у `tools/`; збережіть структуру каталогів. Старіші пакети, зокрема `v0.1.5-beta.6`, не містять цих скриптів і натомість потребують відповідного архіву джерел. Пакет не містить зібраного образу USB-транспорту. OCI-артефакт випуску сервера керування має інше призначення.

## Походження джерел і артефактів

Основою є `python:3.12.14-slim-trixie`, закріплений за `sha256:44ff437bba879d4941b710a369a8f19266aea34b29002807f0c487fabc9eec9b`. Основу, інструкцію APT та встановлення `websocket-client==1.9.0`, зафіксоване хешем, перевірено в [PR 128, ревізія b4181bf](https://github.com/open-ott-play/ottplay-control-server/tree/b4181bff35faff9a27c9bc1e86b0004c43ad1efc/deploy/android-manager). Текст інструкцій збережено для повторного використання наявного кешу збирання. Необов’язковий пакет WebSocket підтримує наявні універсальні клієнти обслуговування; перенесені адаптери CDP також можуть використовувати лише стандартну бібліотеку Python.

Цей рецепт видаляє встановлений пакет `pip` після встановлення зафіксованого wheel, виключає код менеджера й відновлення з PR 128, запускає ADB на передньому плані та вимикає успадковані перевірки працездатності. Видалення інсталятора із середовища виконання зменшує доступну поверхню атаки; це не доказ сканування без виявлених вразливостей.

Перевіреним артефактом PR 128 був `sha256:f2ed00bac5b137c1a4bd18db8f7675677e7c36d4444618eec8f996e205531a6a`. Він містить іншу точку входу та несумісну перевірку працездатності за heartbeat. Це довідковий артефакт, а не збірка цього Dockerfile. Не приписуйте цьому рецепту його ID образу, походження джерел чи результати сканування.

Репозиторії APT не закріплені за знімками. Тому майбутнє чисте збирання може вибрати новіші пакети ОС навіть з тим самим дайджестом основи й хешем Python wheel. Під час кваліфікації збірки запишіть точну ревізію джерел, збирач/платформу, отриманий ID образу, версії пакетів і сканування. Продукційна конфігурація має використовувати цей кваліфікований незмінний ID або дайджест.

## Збирання без порушення роботи зайнятого USB-хоста

Бажано збирати й сканувати на окремому збирачі. Цільовому хосту потрібен лише кваліфікований образ, а не завантаження пакетів чи інструментарій збирання.

Повторно використовуючи підготовлений локальний збирач, спершу перевірте наявність точної основи й кешованих шарів встановлення APT та wheel. Завантаження лише фінального образу PR 128 не підтверджує жодної умови. З кореня репозиторію чи розпакованого каталогу розгортання навмисно автономна спроба виглядає так:

```sh
docker image inspect python:3.12.14-slim-trixie@sha256:44ff437bba879d4941b710a369a8f19266aea34b29002807f0c487fabc9eec9b
docker build --pull=false --network=none \
  --tag ott-android-transport:review \
  deploy/android-usb-manager
docker image inspect ott-android-transport:review
```

`--network=none` стосується кроків збирання; це не загальна гарантія, що збирач ніколи не звернеться до реєстру під час визначення основи. Перед використанням на обмеженому хості підтвердьте локальне визначення основи. Якщо шару APT або wheel немає, зупиніть спробу, а не дозволяйте мовчки мережеве перезбирання на USB-хості.

BuildKit включає мережевий режим кроку до ключа кешу. Тому кеш, створений у стандартному мережевому режимі, може не підійти для наведеної автономної спроби. Використовуйте його лише після перевірки точної основи й ланцюжка інструкцій та зупиніться, якщо будь-який крок встановлення пакетів виконується замість повідомлення `CACHED`. Завершальне видалення `pip` явно використовує `RUN --network=none`; мережа йому не потрібна, навіть якщо попередні кешовані кроки використовують початковий режим.

Перед зміною продукційної конфігурації перевірте версії Python та ADB, проскануйте саме отриманий образ, перевірте передавання бінарних файлів і підготовку APK, а тоді виконайте перевірки приймання з посібника: ідентичності пристрою, авторизації ключів, сну й завантаження. Взаємодію ADB 34 зі старим Android потрібно тестувати; номер версії сам по собі не підтверджує сумісність із KitKat чи Fire. Збережіть поточний образ і приватну резервну копію розгортання, доки відкат не стане непотрібним.

## Ресурсний бюджет виконання

Менеджер хоста, а не цей Dockerfile, встановлює 256 MiB пам’яті, 256 MiB пам’яті разом зі swap та CPU shares 128, без жорсткої квоти CPU чи PID. Він примусово застосовує `--no-healthcheck`, `--network none`, кореневу файлову систему лише для читання, вилучені capabilities та точне зіставлення USB-вузлів. `/tmp` — обмежений tmpfs, що споживає той самий бюджет пам’яті. Адаптер підготовки пише блоками 1 MiB й обмежує один вантаж до 128 MiB; операції поділяють блокування менеджера.

Docker документує відмінність між [керуванням пам’яттю, swap і CPU shares](https://docs.docker.com/engine/containers/resource_constraints/) та [параметром `--no-healthcheck`](https://docs.docker.com/reference/cli/docker/container/run/#no-healthcheck).
